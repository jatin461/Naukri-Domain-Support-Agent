# Governance: the four-layer model (Data, Model, Application, Runtime)

Scope. The brief names concrete controls for two of the four layers: the Application layer (least autonomy and risk classification) and the Runtime layer (per-request budget). Those two layers are enforced in code and demonstrated in transcripts. The Data layer and the Model layer are also described below, so all four layers are applied; their controls are the ones the system already has, listed here with the file that enforces each.

## Data layer

All data is fabricated: `dataset.py` generates the 60 job applications from a fixed seed, the knowledge base was written for this project, and no record describes a real person. The one fixed-format personal field, the phone number in contact details, is masked by a single function (`mask_phone`) before text reaches the model, the session history, an added document or the request log, so it never reaches disk in the clear; candidate names, expected salary and background-check results are acknowledged as out of scope for this pattern-based masker. The lookup tool returns one application at a time and bulk requests such as "list all salaries" are refused, the log stores masked question text and counters but never the answer, and session memory lives only in process memory and is dropped when a WebSocket client without a named session disconnects. The vector index (`chroma_db/`) and the live log (`logs/requests.jsonl`) are git-ignored and rebuilt locally, which mirrors the knowledge base's own 12-month applicant-data-retention rule: nothing about a request is kept beyond what the running service needs.

## Model layer

Every language-model call in graded runs goes to one deterministic, offline mock (`src/llm/mock_llm.py`): the same input always gives the same output, no API key exists in the repository, and every call is counted and recorded by purpose (grounded answer, crew, review, judge) so it can be audited. Setting `MOCK_LLM=false` raises `NotImplementedError` instead of silently switching to an unreviewed live model. The embedding model is pinned (`sentence-transformers/all-MiniLM-L6-v2`, loaded from the local cache with `HF_HUB_OFFLINE=1`), every library is pinned to an exact version in `requirements.txt` and `requirements.lock`, and CrewAI, ChromaDB and Hugging Face telemetry are disabled before those libraries are imported. Model behaviour is bounded by measured, not assumed, settings: the "I don't know" threshold was calibrated on real similarity scores, every crew output and review verdict must validate against a Pydantic schema, and the limits of the rule-based judge and the lexical groundedness check are stated openly.

## Risk classification

**Classification: Medium**

The agent is an employer and candidate support assistant: it answers hiring-policy questions from a fixed 12-document knowledge base and reads one application's status, expected salary and escalation score from a fabricated dataset, which puts it with the customer-support-ticket class of the scheme and above plain summarisation (Low). It is read-only, it does not rank, shortlist, reject or select any candidate, it makes no compensation decision, and the escalation score only routes a case to a human reviewer. Every answer is also checked by a groundedness guard and by an independent two-agent review before it is delivered. The data it touches belongs to the hiring process, which is why it is not Low, but because it takes no consequential hiring decision it is not High. If it were ever changed to rank, score or decide on candidates it would become High and the whole control set would have to be re-assessed.

## Least autonomy

Only the Lookup Agent may call `check_job_application_status`. The restriction is enforced in code, not by convention: `src/governance/autonomy.py` holds an allow-list of tools per agent role (Retrieval Agent: `rag_lookup`; Lookup Agent: `check_job_application_status`; Response Composer: none) and `build_agents` calls `check_agent_tools` before constructing each agent, so wiring the lookup tool to the Retrieval Agent, the Composer or any other role raises `AutonomyViolation` and no crew is produced. Each agent also gets exactly one tool and delegation is off, the mock LLM chooses tools only from the calling agent's own tool list, and a test inspects the configured crew and checks that the lookup tool object is held by the Lookup Agent alone and that lookup invocations occur only on requests routed to it.

## Runtime budget

Each request has a token budget of 1,000 tokens (`MAX_REQUEST_TOKENS`). In `MOCK_LLM` mode the estimate is deterministic: `ceil(len(masked question) / 4) + 600`, where 600 is a fixed allowance for agent prompts, retrieved context and the review prompt; the simulated cost is the estimate divided by 1,000 times USD 0.002, an illustrative rate. A request whose estimate exceeds the cap is rejected after input validation, phone masking and injection detection and before the crew is built, with HTTP 413 and a structured body containing the estimate and the limit. No provider is called in `MOCK_LLM` mode, so nothing is actually charged; the budget is a simulated operational control that would cap spend if a real model were connected.
